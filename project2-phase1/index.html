N1

What LangChain is, and what a chain actually does

Calling an LLM API directly is a one-shot transaction: you type out the entire prompt by hand every single time, fire it off, and get back a blob of unstructured text with no memory of what happened before it. LangChain doesn't replace the API call — it wraps it in reusable pieces so I'm not rebuilding the same plumbing for every project. The three pieces that matter most are the LLM wrapper (a consistent interface so I can swap Gemini for Groq without rewriting my logic), the prompt template (a prompt with blanks I fill in later), and the chain itself — a fixed pipeline of prompt template → model → output, wired together as one repeatable unit instead of three separate steps I have to babysit. A parser gets added onto that pipeline only when I need the output in a specific structure, like the JSON example in the next section.

The piece that actually connects them is LCEL — LangChain Expression Language — which uses the | operator the same way a Unix pipe works: the output of whatever is on the left becomes the input to whatever is on the right. So a chain is really just a sentence written in pipes.

Raw API call

# every time, from scratch
prompt = f"Write a tagline for {name}"
response = client.chat(prompt)
# response is just a plain string
print(response)

A chain (LCEL)

# built once, reused forever
template = PromptTemplate.from_template(
    "Write a tagline for {name}"
)
chain = template | llm | StrOutputParser()
chain.invoke({"name": name})

The difference isn't that the chain is smarter — it's that the chain is a unit. I can reuse it, swap out the model, or drop in a different parser without touching the rest of my code.

N2

Prompt templates & output parsers

A prompt template solves a boring but real problem: I don't want to retype the same instructions every time I just need to change one word. I write the prompt once with a placeholder like {product_name}, and every future call just fills that blank in.

An output parser solves a completely different problem. By default, an LLM's reply is free-flowing text meant for a human to read — which is exactly what makes it painful for code to use reliably. If I ask for "a name and a price" in plain English, I might get a full sentence back, or a bullet list, or something with extra commentary attached. An output parser tells the model to reply in a fixed structure — usually JSON matching a schema I define with a Pydantic model — so my code can just read result["price"] instead of trying to regex a sentence apart.

Plain prompt

"The wireless mouse is called Glide, and it costs $24.99."

Correct, readable — and completely unpredictable in shape.

→

With JsonOutputParser

{
  "name": "Glide",
  "price": 24.99
}

Same answer, but now result["name"] just works.

N3

Memory & tool-calling

By default, an LLM is stateless — every call is a stranger meeting you for the first time. It has no idea what you asked five minutes ago unless you tell it. Memory is nothing mysterious: it just means keeping a running log of the conversation and feeding that whole log back in with every new message, so the model can act like it "remembers" what came before.

Tool-calling is a different kind of upgrade. Instead of the LLM guessing an answer purely from what it already knows, I give it access to real functions — a calculator, a web search, a database lookup — and let the model itself decide when a tool is needed and what to pass into it. The model doesn't run the function; it just outputs a structured request, my code executes the actual tool, and the result gets fed back to the model so it can finish answering with real data instead of a guess.

The loop back to "Tool" only fires when the model actually decides it needs one — otherwise it skips straight to a reply.

N4

What LangGraph is — and why a chain isn't enough

A chain is a straight line: step one always leads to step two, which always leads to step three, in that exact order, every time. That's fine until the task itself needs a decision — "if the order exists, check stock; if it doesn't, ask for the order number again." A chain can't do that on its own, because a chain doesn't look at its own output and change direction. An agent can: it looks at the current situation and decides what happens next, including skipping steps, repeating one, or picking between two different paths entirely.

LangGraph is what lets me actually build that decision-making system, by describing it as a graph instead of a straight pipe. Four ideas carry the whole framework:

  • NodeOne step in the graph — usually a function or an LLM call that does a specific job.
  • EdgeA fixed connection saying "after this node, always go here next."
  • Conditional edgeA branching connection — "after this node, go to A or B depending on the result."
  • StateThe shared data object that travels through the graph and gets updated as each node runs, so every node can see what happened before it.

Chain — fixed sequence

Same order, every single run. No branching, no looking back.

Agent — adaptive path

Looks at its own result, then picks a path — or loops back and tries again.

My own sketch for the "try it yourself" exercise — a status check with a conditional edge deciding the branch.

Put simply: a chain always does the same steps in the same order; a graph can look at what just happened and choose its own next step. That single difference is why the orchestrator pattern below needs LangGraph and can't be built as a plain LangChain chain.

N5

Orchestrator agents

An orchestrator agent is closer to a manager than a worker. It receives a task, figures out what actually needs to happen, and routes it to whichever specialized agent is built for that job — it usually doesn't do the hands-on work itself. A manager doesn't clean the data or write the report personally; they decide who should, based on what the task needs. In a LangGraph implementation, the orchestrator can act as a routing node that evaluates the incoming task and chooses which specialized agent node should handle it next.

This is exactly why this week mattered before the coding starts. Our upcoming mini-project is built around an orchestrator agent that receives raw data and decides which specialized agent should handle it — and that pattern only works with shared state flowing between agents and a router that can make a real decision, which is precisely what a plain chain can't do but a LangGraph graph can.

The orchestrator never touches the data itself — it only ever decides which agent does.

N6

What this week actually changed for me

Going in, I thought LangChain and LangGraph were basically the same thing with two different names. By the end of the week the real split was obvious: LangChain gives me reusable pieces for talking to a model — templates, parsers, memory, tools — while LangGraph gives me a way to let those pieces make decisions instead of just running in a fixed order. A chain is something I build once and run the same way every time; a graph is something that can look at its own state and choose a different path. Once that clicked, the orchestrator pattern stopped feeling abstract — it's just a node whose only job is routing, sitting on top of the exact building blocks from earlier in the week.

Every node here is something from this week's log: a template and a chain (N1–N2), memory as shared state (N3), LangGraph's decision point (N4), and the orchestrator routing to specialist agents (N5).

Slowing down this week instead of jumping straight into code was the right call for me. Understanding the difference between fixed chains and decision-making graphs made the upcoming hands-on project feel much more manageable.
